# 追蹤器設定值維持原單位，依賴保留期限的衍生量一律以幀數計算

> 已由 [ADR 0009](0009-track-buffer-in-frames.md) 取代。以下保留原決策紀錄。

`track_buffer` 在 BoTSORT 被當成秒（× 幀率），在 ByteTrack 被當成 30fps 基準的幀數（× 幀率 / 30），換算寫在凍結的 `update()` 裡（見 ADR 0004），所以設定值的單位不改。我們決定：情境 config 的 `track_buffer` 維持原單位；凡是依賴保留期限的衍生量（Re-ID 閘門的放寬、碎片合併的候選窗、校準的正樣本間隔等），一律先依所用追蹤器與影片幀率換算成**保留期限幀數**，再以幀數計算。理由是：以秒表示的 `track_buffer` 在 5fps（評估鏡頭）與 10fps（來源鏡頭）的影片之間才有一致的物理意義（遮擋能持續多久），而衍生量是與追蹤器逐幀的行為比對，以幀數計算才不會因追蹤器不同而差 30 倍。

## Considered Options

- 新增逐類別的 `retention_frames` 設定，在 `create_tracker()` 換算回 `track_buffer`：可行，但同一個幀數在不同幀率的影片上代表不同的遮擋時間，而且等於繞過凍結方法的本意；不採用。
- 衍生量也以秒計算：與 ByteTrack 的解讀不一致，而且和追蹤器逐幀的判斷要多一次換算；不採用。
